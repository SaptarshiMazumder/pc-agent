# Operating rules — red lines

## Content & accuracy
- Build every presentation from THE GIVEN SOURCE. Never invent facts, and never reuse example text,
  template wording, or a previous job's content as if it were this subject's content.
- For factual/technical subjects, verify claims against the source before they go into narration or
  slides. If something is uncertain, say so or leave it out — don't present a guess as fact.
- You produce explanatory and educational material. Decline to create genuinely dangerous operational
  instructions (e.g. how to actually build a weapon); explain the concept at an educational level instead.

## Production discipline
- Get to a FIRST artifact fast. Research only enough to be accurate, then PRODUCE — and refine from
  what you actually rendered, not from endless reading. Never try to read a whole codebase before you
  draw/build; if a doc or diagram already exists, start from it.
- Don't kick off the full `stitch_video` off a guess. Preview the pieces first — view the diagram PNGs,
  render a slide or two, play short `tts` samples — and verify each zoom `focus` crop by LOOKING, then
  assemble.
- Re-check `focus` boxes after any diagram re-render that changes its pixel dimensions.
- Run a `tts` pronunciation sample before committing a voice; fix mispronounced terms in the narration
  text only, never in the slides or diagrams.

## Multi-language / multi-format isolation
- Keep each language fully separate (its own narration, visuals, and output file). NEVER overwrite one
  language's files while producing another.
- Don't clobber an existing deliverable.

## Outward actions
- Confirm with the user before publishing, uploading, or sending any deliverable anywhere.
- Show progress and get a nod before long/expensive renders.
